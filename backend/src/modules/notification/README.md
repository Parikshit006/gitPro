# GitPro Notification Module (`src/modules/notification/`)

## Overview
The **Notification Module** is a multi-channel delivery engine responsible for dispatching engineering reports and alert digests across **Email**, **Slack**, and **Webhook** endpoints. It is built for enterprise reliability, incorporating automatic retries on temporary failures, execution timeouts, seamless channel fallback, and audit logging.

---

## Strict Architectural Principles

### 1. Complete Decoupling from Report Generation
Why do Notifications know nothing about report generation?
- **Single Responsibility Principle**: The Notification module owns **only delivery and transport routing**. It never synthesizes metrics, calls AI providers, or formats Markdown/HTML strings. It consumes pre-synthesized `ReportDTO` or `ReportResult` payloads generated by `ReportService`.
- **Asynchronous & Scheduled Dispatch**: Decoupling allows reports to be generated in background worker queues or scheduled cron jobs and subsequently dispatched without blocking UI threads.

### 2. Interchangeable Delivery Providers (`INotificationProvider`)
Why are providers interchangeable?
- **Interface Uniformity**: Every transport mechanism (`EmailProvider`, `SlackProvider`, `WebhookProvider`) implements `INotificationProvider.send(request: NotificationRequest): Promise<NotificationResult>`.
- **Zero Service Conditional Logic**: `NotificationService` resolves the appropriate provider from a registry map. Adding SMS, Microsoft Teams, or PagerDuty requires zero changes to the service orchestration logic—simply register a new class implementing `INotificationProvider`.

### 3. Resilient Delivery (Retries, Timeouts & Fallback)
- **Automatic Retries**: Temporary network glitches or rate limits trigger automatic linear/exponential backoff retry loops (configurable up to `maxRetries`).
- **Strict Timeouts**: Every provider execution is wrapped in a `Promise.race()` against a timeout boundary (`timeoutMs`), preventing hanging HTTP requests or SMTP connections from exhausting server resources.
- **Automatic Fallback**: If a primary delivery channel (e.g., `EMAIL`) exhausts all retries and fails, `NotificationService` automatically intercepts the failure and attempts delivery via a secondary fallback channel (e.g., `SLACK` or `WEBHOOK`) when configured in `request.metadata?.fallbackChannel`.

## Layering & Delivery Flow

```
[HTTP POST /notifications/* or Scheduled Worker]
                  │
                  ▼
         [NotificationController] (HTTP payload parsing)
                  │
                  ▼
         [NotificationService] (Orchestrates retries, timeout & fallback)
                  │
                  ├─────────────────────────────────┐
                  ▼                                 ▼
       [NotificationRepository]         [Provider Registry Map]
       (Audit logging & contacts)                   │
                                                    ├──────────────┬──────────────┐
                                                    ▼              ▼              ▼
                                             [EmailProvider] [SlackProvider] [WebhookProvider]
                                                    │              │              │
                                                    ▼              ▼              ▼
                                              (SMTP Server)  (Slack API)    (HTTP Webhook)
```
