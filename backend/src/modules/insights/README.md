# Engineering Insights Module (`src/modules/insights/`)

## Overview

The **Engineering Insights Module** represents the intelligence synthesis layer of the GitPro Engineering Intelligence Platform (Sprint 6). While earlier sprints built the foundational ingestion pipelines, structural graphs, metrics calculators, and raw reporting dashboards, this module transforms mathematical metric scores into **human-understandable explanations, organizational risk evaluations, and actionable engineering recommendations**.

Currently implemented components:
1. **`insight.types.ts`**: Pure, frontend-facing readonly Data Transfer Object (DTO) contracts defining the structure of executive summaries, specialized metric explanations, and prescriptive intervention items.
2. **`insight.repository.ts`**: Dedicated data retrieval repository owning all Prisma database queries required by the insight domain without performing interpretation or calculations.
3. **`insight.service.ts`**: Deterministic engineering recommendation engine that evaluates precomputed metric thresholds to diagnose risks and synthesize executive briefings without LLM invocations.

---

## Architectural Principles & Rationale

### 1. Why Deterministic Rules
A foundational architectural mandate of GitPro is that all core engineering insights and prescriptive recommendations are generated via a **100% deterministic, rule-based evaluator tree**. The service **strictly prohibits invocations to OpenAI, Anthropic, or external Large Language Models (LLMs)** during evaluation:
- **Mathematical Reproducibility**: Given the exact same precomputed metric records, our rule trees are mathematically guaranteed to generate identical summaries, risk levels, health scores, and recommendation checklists every single time.
- **Zero Hallucination Risk**: LLMs are statistically prone to hallucinating architectural dependencies, inventing fictitious file owners, or generating irrelevant advice. Deterministic threshold branches strictly reference verified persistence records from PostgreSQL.
- **Microsecond Execution Latency**: Executing strict in-memory threshold evaluations (e.g., `if (busFactor <= 1) return CRITICAL;`) completes in sub-milliseconds, whereas external LLM APIs introduce unpredictable 2–5 second network latency and ongoing token costs.
- **Air-Gapped & Offline Security**: Enterprise codebases containing proprietary intellectual property operating in isolated VPCs or air-gapped on-premise environments can generate executive engineering intelligence without transmitting metadata to commercial AI vendors.

### 2. Why Metrics Remain the Source of Truth
The Engineering Metrics Framework (`src/modules/metrics/`) owns all algorithmic graph calculations (such as ownership percentages, churn ranks, and bus factor maintainer pools). The persistence snapshots generated by those calculators (`MetricResult`) serve as the **immutable single source of truth** across the entire GitPro platform.
`InsightService` never recalculates ownership ratios, never traverses git graphs, and never reads commit logs directly from disk. It strictly consumes precomputed data via `InsightRepository`. This guarantees strict mathematical alignment between raw analytical charts on the Dashboard and diagnostic risk reports in the Insight domain.

### 3. Why Recommendations Are Reproducible
Every recommendation item generated by `InsightService` originates from an explicit, documented threshold condition rather than generative AI text synthesis:

| Metric Domain | Evaluated Condition | Assigned Risk Level | Deterministic Recommendation & Action Items |
| :--- | :--- | :--- | :--- |
| **Bus Factor** | `score <= 1` | `CRITICAL` | **Cross-train at least one additional engineer.** (Identify primary maintainer, schedule pair programming, mandate peer review). |
| **Bus Factor** | `score == 2` | `HIGH` | **Require mandatory reviews from second contributor.** (Enforce mandatory code reviews, create architectural docs). |
| **Bus Factor** | `score == 3` | `MEDIUM` | **Expand maintainer distribution across teams.** (Encourage collaborative reviews on high-ownership files). |
| **Code Ownership**| `owner > 80%` | `HIGH` | **Reduce knowledge silo.** (Assign bug fixes to non-primary authors, require code walk-throughs). |
| **File Hotspots** | `churn > 50` | `MEDIUM` / `HIGH` | **Refactor module.** (Conduct complexity analysis, increase unit test coverage, decompose monoliths). |
| **Commit Activity**| `daysInactive > 30`| `LOW` (`INFO`) | **Review repository health.** (Confirm active support status, check for stale PRs or security alerts). |

## Service Orchestration Contract (`insight.service.ts`)

The service exposes two primary public orchestration endpoints:

1. **`getRepositoryInsights(repositoryId: string): Promise<RepositoryInsight>`**
   - Retrieves repository metadata and precomputed metrics via `repository.findRepositorySummary(repositoryId)`.
   - Executes deterministic evaluations for Bus Factor, Code Ownership, Hotspots, and Activity.
   - Computes a consolidated `overallHealthScore` (0–100) and assigns an `overallRiskLevel`.
   - Returns an immutable, frontend-ready `RepositoryInsight` DTO.

2. **`getExecutiveSummary(): Promise<ExecutiveSummary>`**
   - Concurrently retrieves all tracked repositories and registered contributors.
   - Leverages `Promise.all()` to evaluate `getRepositoryInsights` concurrently across all workspaces.
   - Aggregates multi-repository health scores into an `overallOrganizationHealthIndex` and isolates `topOrganizationalRisks`.
   - Returns a high-level executive briefing tailored for VPs of Engineering and Engineering Managers.
